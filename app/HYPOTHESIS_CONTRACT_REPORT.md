# Hypothesis contract repair — 4 October 2026

User reported `[hypothesis_invalid]` in the deployed direct-mode application. This category means a parsed model response failed hypothesis validation; it does not identify the specific failed field. Initial checkout clean on `main / e282a87` (`fix: live AI`). No provider credential or private environment was read/edited. No real provider call, commit, push or deployment performed.

## Confirmed contract defects and changes

The model's previous `schema` shape placed descriptive instructions in enum fields: strength was `plausible for source breaches, insufficient for only proposed review signals`; action type and owner role similarly contained combined choice descriptions. The validator requires literal enum values. The old shape also used generic fact/citation placeholders and did not fully communicate alphabetic hypothesis IDs, exact metadata, mandatory checks or forbidden narrative terms, including negated certainty terms.

Before-fix tests reproduce that the supplied example itself fails validation and that hypothesis errors collapse into the same category: [failing TAP](verification/hypothesis-before.tap). This demonstrates the contract defect; the user's exact rejected field remains unknown because no raw deployed model output was inspected.

`analysis-contract.ts` now builds a directly valid source-bound shape example using eligible facts, signal IDs, permitted mechanisms, supporting IDs and an eligible normal baseline. Literal strength/type/owner metadata replace descriptions. The model is instructed to compose its own concise engineering narrative, while preserving valid metadata or choosing from explicit allowed values. The example is not a diagnosis or a canonical inference requirement.

`outputRules` describes required unit/calibration/timing and engineering review/inspection checks, per-signal maximum qualitative strength, counter-evidence, unique alphabetic IDs, role/type choices and exact narrative constraints. Regex restrictions are exported from the existing validator and shared with the contract, avoiding a second divergent list. Five historical context sizes measured from 27,305 to 32,415 bytes, below the unchanged 60,000-byte bound.

The validator's previous combined hypothesis guard is split into the **same predicates**, each with a specific controlled error. Identity, narrative, missing checks, metadata, strength, signal IDs, mechanism/signal linkage, supporting context and normal counter-evidence now have distinct diagnostic codes. Existing accepted/rejected domain rules are preserved; no model fact, citation, certainty or malformed field is automatically rewritten or accepted. Unknown numbers/units/assets/times, future/historical evidence in prospective mode and inflated strength remain rejected.

Files: new `src/lib/analysis-contract.ts`; `src/lib/analysis.ts`, `analysis-validation.ts`, `analysis-response.ts`; `tests/repair.test.ts`, `tests/direct-browser.spec.ts`, `scripts/verify-direct-browser.ts`; README, IMPLEMENTATION_STATUS and this report. CSS/layout, data/originals, direct access configuration, local actions/workflow, optional protected guards, response parsing, timeout/token caps and dependencies/lockfile unchanged. No extra provider call or automatic retry was added.

## Deployment and limits

Keep the existing four direct-mode environment variables. Deploy this revised code separately and explicitly request composition. The request now supplies a valid, source-bound example and comprehensive allowed values. If a model still violates the contract, the UI names the failed rule rather than accepting unreliable output.

Real SumoPod/model compliance is **NOT TESTED**. Previous unauthenticated read-only access to the user's Vercel URL was blocked by Vercel Authentication; no bypass or provider POST attempted. Local fixture acceptance proves the contract is satisfiable, not that the deployed model will comply or its inference is correct. Other browser engines/physical devices and industrial validation are also untested.
